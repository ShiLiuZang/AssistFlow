# 降低回复时延

一轮对话的耗时主要在串行的模型调用上。优化前各分支要经过的步骤（括号里是是否调用模型）：

| 分支 | 步骤 |
|---|---|
| 问候、转人工 | 意图识别（模型） |
| 知识咨询 | 意图识别（模型） → 检索（向量化 + 召回 + 精排） → 证据充分性检查（模型） → 生成回答（模型） |
| 退款、售后政策 | 意图识别（模型） → 查订单 → 查询改写（模型） → 逐个检索 3 个查询 → 统一精排 → 证据检查（模型） → 生成回答（模型） |
| 订单、物流 | 意图识别（模型） → 工具调用循环（模型） |

## 做了什么

1. **意图规则**（`app/core/intent.py` 的 `quick_intent`）
   - 整句只是问候（“在吗”“你好”）或只是要人工（“转人工”“人工客服”）时，不调用模型识别意图。
   - 只认整句匹配，所以“不要人工”“人工审核要多久”“在吗 我的快递呢”仍交给模型判断。
2. **预取检索**（`app/graph/prefetch.py`，在 `classify` 节点里）
   - 意图识别期间先做知识检索。检索不调用模型，只有向量化、召回和精排。
   - 意图是知识咨询就直接用预取的结果，否则取消预取。
3. **预取回答**（`assess_evidence`）
   - 规则闸门（有证据、置信度达标）通过后，证据充分性检查和生成回答同时开始。
   - 检查通过就用回答；检查不通过就取消回答，进入原来的拒答流程。
4. **政策检索并行**（`retrieve_policy_detailed`）
   - 原问题的检索和查询改写同时开始，改写出的查询之间也并行检索。
   - 任一检索出错时取消其余检索，并抛出同一个错误。
5. **精排连接复用**（`app/core/rerank.py`）：以前每次精排都新建 HTTP 客户端，要重新握手；现在复用连接池。模型客户端在 langchain-openai 里本来就复用连接。

预取结果只在输入完全一致时才会使用：`take` 比对请求 ID、问题、证据、订单和摘要，否则重新计算。所以开关预取只改变耗时，不改变回答。每轮结束时，Runtime 会取消没用上的预取。

## 效果

`uv run python -m scripts.latency_bench` 用模拟耗时的模型和检索跑真实的对话图，对比开关优化前后的耗时。模拟耗时为：意图识别 1.0s、检索 0.6s、证据检查 1.0s、回答 2.0s、改写 1.0s、统一精排 0.3s、查订单 0.1s。数值可以在脚本里按线上监控修改。

| 场景 | 优化前 | 优化后 | 节省 |
|---|---|---|---|
| 问候 | 1.05s | 0.03s | 1.0s |
| 转人工 | 1.04s | 0.03s | 1.0s |
| 知识咨询 | 4.66s | 3.04s | 1.6s |
| 退款政策 | 7.28s | 5.07s | 2.2s |

知识咨询的耗时从“识别 + 检索 + 检查 + 回答”变成“max(识别, 检索) + max(检查, 回答)”。

## 代价

- **预取检索**：意图不是知识咨询时，会多一次向量化和一次精排请求。这类调用不消耗模型 token，但精排服务按次计费或有限流时要留意。
- **预取回答**：证据检查不通过时，会多一次生成回答的模型调用。不通过的比例可以从问题池里来源为 `self_check` 的记录估算。
- 两项都可以单独关闭：`SPECULATIVE_RETRIEVE=false`、`SPECULATIVE_ANSWER=false`。意图规则用 `INTENT_RULES=false` 关闭。
- 预取的模型调用在观测里挂在前一步的 span 下（例如回答的 `answer_model` 挂在 `evidence_check` 下），token 用量的统计不受影响。

## 没做的

- **订单、物流分支的工具调用循环**：每一步都要等模型决定下一步，无法预取。可以考虑给常见的“查物流”走固定流程，不经过模型决策。
- **更快的模型**：意图识别和证据检查可以换用更小、更快的模型，需要先用 `scripts/eval_intent.py` 评估准确率。
- **流式输出**：电商渠道整条发送，流式只对网页有意义。
