# 阶段 3：拼多多渠道接入 设计说明

目标：拼多多店铺的买家在拼多多聊天窗口里提问，由本系统的 AI 回答；需要人工时进入坐席工作台，坐席的回复发回拼多多。网页咨询的行为不变。

## 平台现状与接入方式

拼多多没有给普通开发者公开的客服聊天收发接口。要合规地拿到买家消息，需要满足下面任一条件：

1. 以客服类服务商（ISV）身份在拼多多开放平台申请客服消息相关权限。具体接口名、消息格式和推送方式在获批后的文档里，以那份文档为准。
2. 使用店铺已经在用、并且获得平台授权的客服中间件，由它提供消息回调和发送能力。

网上常见的做法是模拟登录商家后台，或者劫持客服客户端、网页的长连接。这违反平台规则，有封店风险，本项目不实现。

所以本项目不直接连拼多多，而是定义一个“渠道桥”接口：

```
拼多多 ⇄ 渠道桥（上面两种方式之一，由店铺自行对接） ⇄ AssistFlow
```

平台接口的变化、授权令牌和长连接都留在桥里。AssistFlow 只认一个稳定的签名接口，桥可以单独替换。

## 渠道桥协议

两个方向的签名方式相同：

```
X-AssistFlow-Timestamp: Unix 秒
X-AssistFlow-Signature: hex(HMAC-SHA256(PDD_BRIDGE_SECRET, 时间戳 + "." + 请求体原文))
```

时间戳与本机相差超过 5 分钟的请求一律拒绝。

**入站**：`POST /api/channels/pinduoduo/events`，返回 202。

```json
{
  "shop_id": "店铺 ID",
  "events": [
    {"msg_id": "平台消息 ID", "buyer_id": "买家 ID", "type": "text", "text": "在吗", "sent_at": 1700000000},
    {"msg_id": "…", "buyer_id": "…", "type": "order", "order_sn": "231003-123456789012345", "goods_name": "保温杯", "text": ""},
    {"msg_id": "…", "buyer_id": "…", "type": "goods", "goods_name": "保温杯", "text": "有现货吗"}
  ]
}
```

- `type` 取值：`text`、`goods`（商品卡片）、`order`（订单卡片）、`image`、`video`、`emoji`、`other`。
- 返回 `{"accepted": [...], "duplicates": [...]}`。同一 `msg_id` 重复推送不会重复回答，所以桥可以放心重试。
- 本服务登记消息后立即返回，不等 AI 回答。

**出站**：本服务向 `PDD_BRIDGE_SEND_URL` 发 `POST {shop_id, buyer_id, text, idempotency_key}`，桥负责发给买家。

- 网络错误、429、5xx 会重试 3 次（间隔 1、2、4 秒），其他 4xx 不重试。
- 每条发送结果都记录在 `channel_messages`。
- 发送地址为空时是演练模式：回复只记录，不发送。

## 数据表（迁移 `c130001`）

- `channel_sessions`：店铺加买家对应一个内部顾客 ID（`pdd-` 加随机串）。
  - 平台买家 ID 只存在这张表里，只用于回发消息。会话、日志、坐席工作台里看到的都是内部 ID。
  - `conversation_id` 指向当前会话。买家隔 `CHANNEL_IDLE_MINUTES`（默认 24 小时）再来时开新会话；人工接待未结束时不开。
- `channel_messages`：收发记录。
  - 入站消息按平台消息 ID 去重，状态依次为 `pending`、`done` 或 `failed`。进程重启时，最近 10 分钟内还没处理的消息会补处理，更早的标为 `expired`。
  - 出站消息的状态为 `sent`、`failed` 或 `dry_run`，并记录重试次数。
  - `created_at` 由应用按 UTC 写入，不依赖数据库时区。
- `channel_orders`：订单归属。见下方“订单”。

## 一条消息的处理

1. **合并**：买家常把一句话拆成几条连发。同一买家静默 `CHANNEL_MERGE_SECONDS`（1.5 秒）后，把这几条合成一轮，最多等 `CHANNEL_MERGE_MAX_SECONDS`（6 秒）。同一买家的消息串行处理，不同买家并行处理。
2. **人工接待中**：消息直接进坐席队列，AI 不回复。图片会给坐席留一条“请到商家后台查看”的提示。
3. **明确要人工**：整句只是“人工”“转人工”“我要人工客服”这类话时，直接进排队，不经过模型和图。这样模型或图出问题时，买家也能按兜底话术回复「人工」转出去；有待确认的建单或选单时同样放行。
4. **待确认操作**：网页上用按钮完成的操作，在渠道里改为文字。
   - 建单：买家回复“确认”“好的”“可以”等即提交，回复“取消”“算了”等即放弃。说别的内容会再提示一次。
   - 选订单：买家回复序号或订单号，或者回复“取消”。
5. **其他消息**：走一轮图，复用网页聊天的同一套流程（`stream_graph_chat`），两个入口的行为一致。
6. **安抚**：超过 `CHANNEL_HOLD_SECONDS`（8 秒）还没答完，先发一句“正在为您查询，请稍等～”，避免平台把这轮算作超时未回复。
7. **出站整理**：
   - 去掉 Markdown 和 `[1]` 这类引用编号。
   - 去掉外部链接、手机号、座机、微信号和 QQ 号，因为平台不允许引导到站外。
   - 按句子拆成每条不超过 `PDD_MAX_MESSAGE_CHARS`（500 字）的消息，最多 4 条。
8. **出错**：模型超时或出错时回复“当前咨询较多，请稍后再发一次，或回复「人工」转人工客服”，入站记录标为 `failed`。买家接着问别的问题时，失败的那一轮会补一句“上一个问题没有处理完成”收尾，然后正常回答新问题，会话不会卡住。

## 人工坐席

- 坐席工作台的会话列表和详情会标出“拼多多”来源。
- 以下内容经实时推送回调发回拼多多：坐席回复、“人工客服已接入”、“人工服务已结束”。内部备注不发。
- 同一会话的坐席消息按顺序发送。

## 订单

拼多多买家查订单时有越权风险：任何人都能在聊天里打出别人的订单号。所以只认平台带出的订单卡片。

- 买家发来订单卡片（`type=order`）时，订单登记在该买家名下（`channel_orders`）。同一订单不会再登记给别的买家。
- 订单查询工具和选订单节点对 `pdd-` 顾客只返回登记在其名下的订单。手打的订单号查不到。
- 配置了 `PDD_CLIENT_ID`、`PDD_CLIENT_SECRET`、`PDD_ACCESS_TOKEN` 时，会调用开放平台的 `pdd.order.information.get` 查询状态。
  - 签名规则：MD5(secret + 按键排序拼接的 key+value + secret)，结果取大写。
  - 状态映射：`order_status` 1/2/3 分别对应 待发货/已发货待签收/已签收。`refund_status` 2/3/4 分别对应 售后处理中/退款中/退款成功。
  - 这些字段按开放平台文档整理，接入时请对照当前文档核对。
  - 没配置或查询失败时，只回复商品名，并说明暂时查不到状态。
- 实体识别增加了拼多多订单号格式（6 位日期加一串数字），指代消解和订单节点都能识别。

## 配置

| 变量 | 默认 | 说明 |
|---|---|---|
| `PDD_ENABLED` | false | 开启渠道 |
| `PDD_BRIDGE_SECRET` | | 与渠道桥共享的签名密钥，开启时必须不少于 32 字符，否则拒绝启动 |
| `PDD_BRIDGE_SEND_URL` | | 渠道桥的发送接口；为空时是演练模式 |
| `PDD_CLIENT_ID` / `PDD_CLIENT_SECRET` / `PDD_ACCESS_TOKEN` | | 开放平台应用和店铺授权，用于查订单，可选 |
| `PDD_MAX_MESSAGE_CHARS` | 500 | 单条消息最长字数 |
| `CHANNEL_MERGE_SECONDS` / `CHANNEL_MERGE_MAX_SECONDS` | 1.5 / 6 | 合并连发消息 |
| `CHANNEL_HOLD_SECONDS` | 8 | 安抚消息的触发时间，设为 0 关闭 |
| `CHANNEL_IDLE_MINUTES` | 1440 | 买家隔多久再来算新会话 |

管理员可以在 `GET /api/channels/status` 查看最近 24 小时的收发数量和最近的失败记录。

## 不在本阶段

- 渠道桥本身。它取决于店铺拿到的是哪种授权。
- 多实例部署：合并、排队和实时推送都在进程内存里（阶段 4 换成 Redis）。
- 多店铺各自的开放平台授权：目前一套 `PDD_ACCESS_TOKEN`，买家会话已经按店铺区分。
- 图片理解、商品卡片的详细信息（价格、库存）。
- 平台的敏感词库：目前只处理链接和联系方式，承诺类说法由原有的输出护栏处理。
