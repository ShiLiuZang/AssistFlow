# V2 管理后台：真实数据展示设计

日期：2026-10-01。阶段：本轮现有后台能力的 V2 展示与操作接入已完成，保留原配色与导航。八个管理页面可实时查询；录入、向量补齐、候选处理、待审建议、核准发布、作业启动/停止、RAG 评估与单句分类均复用既有业务接口。隔离写入流程、真实只读查询、材料预览作业及 ONNX 服务启动/停止/恢复和单句推理已验收。真实候选/审核队列为空、向量 pending 为 0，因此没有对真实库执行审核发布、嵌入补齐、训练或模型评估；产品认证及未有接口的能力另行规划。

目标页面位于 `frontend/minihelp-v2/`，接入目标是当前“智能客服”项目的 `app/api/`。本方案以当前源码中的接口、查询范围和状态为依据。它不是 Minihelp 参考项目的接口验收记录；真实验收仅覆盖第 13 节明确记录的范围，不代表完整业务流程已联调。

## 1. 本轮范围与页面结构

沿用 V2 的深色侧栏、浅色内容区、森绿强调色、指标条、子页签、表格和详情弹窗。调整数据组织、字段名称、状态和操作反馈，保持已经选定的视觉风格。

覆盖八个管理页面：管理总览、知识中心、知识缺口、RAG 质量、观测与成本、咨询主题、分类器管理、作业中心。

“原功能对照”继续作为说明页。“设置与权限”暂无成员、权限和配置管理接口，本批保留独立的演示标记，不把它当作真实管理功能。客户咨询、客服工作台、客户资料、商品订单和工单中心不在本批接入范围。

所有管理业务页使用相同的阅读顺序：

1. 页名、业务说明、刷新和当前页的主要操作。
2. 数据来源、统计范围、业务报告时间和本次读取时间。
3. 三至四个核心指标，明确单位与分母。
4. 原有子页签与筛选，展示当前任务的数据表或报告。
5. 点开记录查看原文、依据、处理状态和后续操作。

总览保留现有六模块卡片。作业中心作为各业务页共用的任务入口。

## 2. 全局数据表达规则

| 数据情况 | 页面表达 | 处理方式 |
| --- | --- | --- |
| 首次读取中 | 指标占位、表格加载状态 | 读取完成前不展示上一次演示数据 |
| 接口成功，计数为 0 | 显示 `0`；列表说明“暂无记录” | 明确这是已读取到的空数据 |
| 字段为 null 或尚未读取 | 显示 `—` | 不转换成 0、不参加比率计算 |
| 报告未生成 | “尚未生成报告” | 保留生成报告或查看作业入口 |
| 请求失败或报告损坏 | “读取失败”及重试入口 | 错误说明与业务空状态分开 |
| 某个子模块失败 | 该模块显示失败 | 其余已成功模块正常显示 |
| 刷新失败，有上次成功结果 | 保留结果并标注“上次读取，刷新失败” | 数据时间保持原值 |
| 请求已受理，业务未完成 | 显示“处理中”或返回的实际状态 | 不因 HTTP 2xx 就提示业务成功 |
| 操作部分完成 | 分别展示已完成步骤、失败步骤、下一步 | 例如“原文已保存，向量化未完成” |

数值格式：计数为整数；比例显示百分比并注明分母；MRR、F1 和检索分数使用明确的指标名。未知或零分母显示 `—`。检索相似度不显示为“答案正确率”或“置信度百分比”。

时间格式：列表显示月日与时分，详情显示完整原始时间。报告生成时间与页面读取时间分别标注。当前接口中不少时间未带时区，在后端明确时间约定前，不擅自按 UTC 转换。

字段缺失时不补演示姓名、版本、标题、更新时间或账号角色。接入页不使用示例读数兜底；演示页显式标注“演示数据”。

## 3. 管理总览

数据源：`GET /api/admin/overview` 的 `modules`。

六张模块卡片显示 `title`、`status`、`headline`、`metrics` 和 `note`。指标直接使用接口的 `label/value`，前端负责格式，不自行改造为另一种业务指标。

| 原卡片 | 接入后的读数 |
| --- | --- |
| 知识中心 | 知识块数、待向量化数、Milvus 数量或离线、关键条款数 |
| 知识缺口 | 待审、发布中、已通过、已驳回 |
| RAG 质量 | 已保存报告的策略数、评估题数、最佳 MRR |
| 观测与成本 | 按接口返回的报告状态和读数显示，不固定写“3 个报表正常” |
| 咨询主题 | 实际归类问题数量、命中类目数，说明统计来源 |
| 分类器管理 | 已通过的验收项数 / 总验收项数、服务状态 |

状态文案：`ok=正常`、`attention=需关注`、`missing=尚无数据或产物`、`error=读取失败`。不能把 missing 显示成“运行失败”。

侧边“先处理这些事”优先展示待审、发布中、待向量化和异常模块。只使用有真实计数的任务；没有报告时展示“生成报告”的动作，不伪造待处理个案数。

## 4. 知识中心：第一批重点

### 4.1 知识内容

数据源：统计使用 `GET /api/kb/overview`，全库列表使用 `GET /api/kb/chunks`，完整正文使用 `GET /api/kb/chunks/{id}`。当前后端的核心对象是知识块，不是具有版本和发布生命周期的文档。

| V2 现有表达 | 新表达 | 数据依据 |
| --- | --- | --- |
| 知识总数，单位“篇” | 知识块总数，单位“块” | `chunks.total` |
| 已发布文档 | 已向量化，单位“块” | `chunks.done` |
| 待审核文档 | 待向量化，单位“块” | `chunks.pending` |
| 草稿文档 | 关键条款，单位“块” | `chunks.key_clause` |
| 原页面 Milvus 条数 | Milvus 条数，单位“条” | `milvus.count`，离线与未知分别展示 |
| 原页面双写结论 | 双写核对：一致 / 对不上 / 未知 | `consistent`，仅表示待补状态与数量核对 |
| 适用范围，例如“全部商品” | 内容类型、分类、章节路径 | `content_type/category/section_path` |
| 文档版本 v1.x | 记录 ID；文档版本暂不展示 | 后端没有文档版本字段 |
| 更新时间 | 录入时间 | `created_at`，不能解释为最后修改时间 |
| 草稿 / 待审核 / 已发布筛选 | 全部 / 待向量化 / 已向量化 | 对应当前知识块状态 |

顶部保留原四项并补回 Milvus 实际条数与双写数量结论，共六项；下方仍使用现有表格和详情交互。MySQL 的 done 数不代替 Milvus 条数；数据库或向量库不可读时不把未知结论显示成一致。沿用后端 consistent 判断：pending 为 0 且 done 与 Milvus 数量相同；数量一致不代表逐条向量匹配或检索质量通过。

表格列：知识块 ID、问法与答案摘要、类型与分类、向量状态、录入时间、查看。章节路径可作为内容副行显示。正文按普通文本渲染，保留换行；详情展示问法、完整答案、章节路径、内容类型、关键条款标记和向量状态。

`overview.recent` 仍为最近 12 块、120 字摘要，供兼容旧页面使用。V2 库存表改为独立全库查询，按 ID 降序排列；列表返回前 160 字，点击“查看全文”后单独读取完整答案和元数据，不把摘要当作完整详情。

列表支持全库问法、完整正文、分类与章节搜索，向量状态与内容类型筛选；类型含对话提取与未标注。每页可选 5 / 10 / 20 / 50 块；搜索、筛选和修改每页条数回到第一页。页码以接口返回值为准，超过末页时收敛到最后一页。统计卡保持全库口径，页脚分别显示筛选总数和本页范围。

库存查询只访问 MySQL，不依赖 Milvus 在线。统计、列表与详情分别处理失败；未知结果显示 `—`，不回退展示样例。详情按原始文本保留换行，显示完整字数、章节、分类、录入时间、向量记录和审核关联；字段缺失保留为未提供或未关联。

`sources` 是白名单材料文件的清单和切块预估。可显示材料名、类型、存在状态、字符数、预计块数、文件修改时间；“文件存在”不等于“该文件已入库”。它单独放在“录入与切块”的材料选择区，不能冒充知识文档库存。

### 4.2 录入与切块

保留“左侧输入、右侧预览”的结构。内容类型选项来自 `overview.content_types`，不硬编码演示原型中的 `product` 类型。

| 区域 | 展示字段 | 接口 |
| --- | --- | --- |
| 输入 | 手工 Markdown、内容类型、白名单材料选择 | `POST /api/kb/preview` 接收 `text/content_type` 或 `file` |
| 预览摘要 | 原文字数、切块数、关键条款数、重复数或“未完成查重” | `chars/total/key_clause/duplicates/dedup_known` |
| 切块明细 | 序号、章节、分类、问法、正文、字数、关键条款、表格、重复状态 | `chunks[]` |
| 录入结果 | 新增块数、跳过重复数、生成 ID、向量化结果 | `POST /api/kb/ingest` |

`dedup_known=false` 时，即使 `duplicates=0` 也不能显示“无重复”。单块 `duplicate=null` 显示“未查重”。

按钮采用“预览切块”与“确认录入”，不要使用“保存草稿”或“发布文档”。修改正文、类型或材料后，旧预览立即标为失效，必须重新预览。

录入结果分别显示“原文入库”和“向量化”。若请求提示原文已经入库、向量化失败，保留明确结果并引导“补齐向量”，不要提示用户重新录入。

当前实施：手工正文及类型 → 切块与查重 → 展示完整提交原文并勾选核对 → 调用现有 `POST /api/kb/ingest`。请求固定 `vectorize:false`，不启动整个待向量化队列。新增原文保存为 pending，结果显示实际新增、跳过重复与返回 ID，ID 可打开现有全文详情；库存与总览缓存随后重新读取。白名单材料当前仅展示清单，尚未开放选文件录入。

实时表单初始为空，样例模式不开放写入。修改正文或类型立即使旧预览失效，包括未完成的预览请求。查重未知、空切块或全部重复时禁用入库；提交期间锁定正文、类型、重复提交和数据来源切换。超时、断连、5xx 或不完整响应显示“录入结果待核对”，不自动重试，也不推断未写入；先看库存，再重新预览查重。校验失败保留输入，需重新预览才能核对提交。

### 4.3 对话挖知识

数据源：`GET /api/kb/staging`。这是从对话抽取的候选问答，与“知识缺口”审核队列分开。

| 后端状态 | 展示文案 | 可执行动作 |
| --- | --- | --- |
| extracted | 已抽取，待去重 | 查看抽取结果 |
| kept | 待人工审核 | 查看、采纳、弃用 |
| discarded | 去重已丢弃 | 查看 |
| approved | 已采纳入库 | 查看 |
| rejected | 人工已弃用 | 查看 |

表格列：问题、答案摘要、材料来源、批次、当前状态、操作。待审数量对应 `kept`，不能对应 extracted，也不能与知识缺口 pending 合并。

当前 `rows` 每个状态只返回有限样本，答案截断至 160 字。展示“每个状态最多显示 N 条”；样本条数不是状态总数。完整答案和可信材料需在采纳前可查看。

后端 `staging_stats()` 已返回 extracted/kept/discarded/approved/rejected 五种全量计数，筛选按钮显示对应数量。页脚分别显示当前状态总数和实际读取的有限样本数；不以样本长度代替计数。每个状态的样本读取在 SQL 中限量，默认 30、上限 100。

详情使用 `GET /api/kb/staging/{id}` 读取完整问题、答案、状态、批次、时间与当前可信材料。来源标记必须命中项目材料白名单才能读取文件，未知会话引用或任意路径不作为可信材料。材料可读、缺失、不可信与读取失败分别展示；现有来源校验检查连续原文和问题脱敏，校验通过仍需要人工判断内容质量和适用范围。

材料依据是当前文件，不是抽取时的历史快照，也不代替人工审核结果。暂存记录尚无审核理由、操作人及已入库知识块的关联字段，页面明确说明未提供。实时模式可重新核对 kept 状态与材料校验后采纳或弃用；采纳调用原后端全库 pending 向量补齐，包含历史待补块，确认页明确范围。部分失败可能已保存原文，先核对库存与状态后再恢复；不自动重试。

### 4.4 索引状态

四项读数：MySQL 知识块总数、已向量化、待向量化、Milvus 向量数。

状态判断使用 `db_error`、`milvus.online` 和 `consistent`：

- MySQL 读取失败：原文统计显示 `—`，说明库存读数不可用。
- Milvus 离线：显示“向量库不可用”，向量数显示 `—`。
- `consistent=null`：显示“暂无法核对”。
- `consistent=false`：显示“数量不一致或仍有待向量化”。
- `consistent=true`：显示“两端数量一致”。这不是逐条内容一致或检索质量的证明。

去掉目前演示索引表中虚构的“来源文档版本”和逐文档索引状态。用类型分布、最近知识块状态、知识作业状态取代。主要动作是“核对并补齐向量”。现有直接接口 `POST /api/kb/vectorize` 保留；V2 复用长任务接口 `POST /api/jobs/kb-vectorize` 启动作业，用 `GET /api/jobs/kb-vectorize` 读取状态与最多 400 行日志。

原文录入结果提供“查看索引并补齐”入口，不自动启动。确认前重新读取库存和作业；待补为 0、读数未知、向量库离线或相同作业已运行时不能启动。确认范围是启动时全库 pending，包含历史待补块；会调用嵌入服务，现有处理范围与核心逻辑保持不变。

索引页每 3 秒查询运行状态，不用计时推测进度；离开该页停止本页轮询。进程 ok/failed/stopped 后重读库存，不把进程状态直接当成数量或质量结论。批次失败可能已有原文完成，结果提供剩余 pending 明细与日志，不要求重录。启动超时、5xx 或响应不完整时先查询真实状态，不自动重试；409 读取既有运行；查询失败不声称作业已停止。idle 加旧日志明确说明服务重启可能清空运行记录。样例模式不启动任何作业。

### 4.5 检索自测

数据源：`POST /api/kb/search`，输入 `q/strategy/top_k`。

结果卡显示排名、问法、答案、章节、类型、分类、检索分数和重排分数。两种分数分别命名，缺失重排分数显示 `—`。搜索无命中与检索请求失败使用不同文案。

选择问题后才发起检索，页面加载不自动调用模型。若后续加入回答测试，则单独接 `POST /api/knowledge/answer`，展示回答、拒答状态和引用，不把检索命中列表冒充生成回答。

## 5. 知识缺口

数据源：`GET /api/review/queue?page=…&size=…&q=…&status=…`、`GET /api/review/{id}`、`GET /api/review/materials/{source_ref}`；全量状态读数复用 `/api/admin/overview` 的 review 模块。

顶部指标：待审、发布中、已通过、已驳回。表格列：标准问题、归并频次、状态、来源摘要、创建时间、审核人、操作。

详情分为三块：原始问题与来源、当时检索快照、人工确认答案与可信材料。明确区分 AI 建议和人工确认答案，不能将建议预填后直接视为已批准。

状态使用 `pending/publishing/approved/rejected`。目前原型里的“已解决、无需处理”不要直接套到这个队列。

通过审核调用 `POST /api/review/{id}/approve`，填写 `approved_answer/source_ref`。发布失败可能返回 HTTP 202，页面应读取响应中的实际状态和 `publish_error`，显示“审核已保存，待完成发布”。恢复动作调用 `POST /api/review/{id}/publish`，不重新审核。

完整队列使用服务端 total/page/size/pages，支持 10 / 20 / 50 条分页和问题、答案、材料的字面搜索；顶部计数使用全量聚合，不使用列表长度。兼容原页面：未提供 page 时仍返回原 items-only 最多 100 条列表。

人工确认答案与 AI 建议分开，选择白名单材料后可读完整正文及 SHA-256。核准前重新读取审核状态，并校验答案属于材料连续原文；核准、驳回和重试发布分别确认。返回 202 显示“核准已保存，发布尚未完成”；查询 publishing 状态后才可重试发布，复用既有知识块，不重复核准。生成待审建议复用 `POST /api/review/process?limit=20`，说明检索/聊天调用和队列写入范围，不自动核准。

## 6. RAG 质量

数据源：`GET /api/rag-eval/report`、`GET /api/knowledge/cases`、`GET /api/knowledge/evaluation-state`。

保留“策略对照”和明细视角。原型中的“编造个案台账”暂改为“逐题评估结果”，因为当前接口没有独立个案的累计、认领和解决记录。

| 展示内容 | 字段与口径 |
| --- | --- |
| 报告信息 | `created_at/k/generation`；区分仅检索与含生成 |
| 策略对照 | `summary[strategy].recall_at_k/mrr/failures/cases` |
| 生成指标 | `refusal_accuracy/keyword_coverage`，仅在报告存在相应字段时展示 |
| 逐题结果 | `details[]` 中的问题、策略、召回、生成结果、预期拒答、实际结果、错误 |
| 固定题集 | `cases[]` 中的问题、期望章节组、应否拒答 |

召回率的分母是有标准证据组的可回答题目；失败次数和总题数另列。关键词覆盖率只是预期关键词是否出现，不能改名为忠实度，也不能据此统计“确认编造率”。

`status=not_evaluated` 时展示“尚未评估”。仅检索报告中的生成指标显示“未评估”，不是 0。服务调用失败留在逐题明细中，不能伪装成普通零分样本。

运行入口复用 `POST /api/knowledge/evaluate`。核对当前固定题集、1–50 的 top_k 与是否生成回答后提交，生成默认关闭。读取现有评估锁，运行时每 3 秒查询状态，409 不重复启动；前端请求时限覆盖原后端 10 分钟上限。没有报告也保留运行入口，失败或超时后先查询状态与报告，不把旧报告当成本次结果。浏览页面不自动启动评测。

## 7. 观测与成本

数据源：`GET /api/observability/overview`。保留现有成本、趋势、校准三个子页，但分别处理 `cost/trend/calibration` 的状态。

成本表显示：意图、请求数、生成调用数、输入 token、输出 token、用量未知次数、未定价次数、分币种估算小计、生成时延 P95。字段来自 `rows[]`，报表信息来自 `meta`，整体完整性来自 `summary`。

不把请求数等同于生成调用数，不把生成时延称为整轮响应时间，不把 token 称为实际账单。金额使用 `priced_subtotals` 的币种，不跨币种相加；费用不完整时标注“估算不完整”，不能显示为全部已计费。报表覆盖的是输入记录中提供的生成调用，不能称为全站实时总成本。

趋势只展示 `trend.runs` 中后端判定可比较的运行。页头说明可比较条件，并显示 `omitted_incomparable`。只有一次运行时展示读数或单点，不虚构上升/下降趋势。

校准展示 `calibration.in_use`、推荐阈值、`in_sync`、扫描结果和 answerable/absent 分布。推荐值与当前值分别表达，不把“查看推荐”设计成已经修改运行配置。

## 8. 咨询主题

数据源：`GET /api/topics/catalog`、`GET /api/topics/distribution`、`GET /api/topics/questions?label=…&page=…&size=…`。

顶部读数：已归类问题数、命中类目数 / 权威类目总数、最新归类时间。类目名称与边界来自 catalog，不使用 V2 自行编写的名称。

左侧类目列表展示名称、问题数及占已归类问题比例，右侧显示所选类目的边界、最多三个代表问法和分页明细。分母使用 `distribution.total`。一条多标签问题会在多个类目计数，因此各类占比之和可能超过 100%，不能当作互斥饼图。

明细表展示问题、全部标签、来源、出现次数、审核状态和归类时间；完整原始问法、归类文本、规范化标识和提问时间进入详情。使用服务端返回的 `page/size/pages/total`，不从当前页长度推算总量。

## 10. 作业中心

数据源：`GET /api/jobs`、`GET /api/jobs/{name}`；操作为 `POST /api/jobs/{name}` 和 `POST /api/jobs/{name}/stop`。

顶部指标：登记作业数、本次服务运行中的运行中数、完成数、失败数。列表列：作业名称、执行条件、是否重任务、状态、开始时间、结束时间、查看日志 / 启动 / 停止。

| 后端状态 | 页面文案 |
| --- | --- |
| idle | 本次服务启动后尚未运行 |
| running | 运行中 |
| ok | 进程执行完成 |
| failed | 进程执行失败 |
| stopped | 已停止 |

“进程执行完成”不等于对应的质量验收通过；完成后刷新业务页的真实报告或库存进行判断。没有后端进度百分比时只显示运行状态和最新日志，不生成进度条百分比。

现有运行状态保存在进程内，服务重启后归零；日志文件可以仍然存在。将“本次运行状态”和“现有日志更新时间”分开显示，不用历史日志时间推造一次已完成的任务。若需要历史运行列表，再补持久化任务记录。

实时详情支持现有 14 项登记作业核对后启动或停止。启动前重新读取状态，确认页列出作用、依赖、资源与日志重建说明；不传命令或自定义参数。停止只用于仍在运行的作业，明确已完成产物不会撤销。运行中每 3 秒读取列表与打开的日志，结束后业务页重新读取报告；样例不执行真实作业。

## 11. 操作反馈与详情统一设计
