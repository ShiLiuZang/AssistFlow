01 / CONTEXT

先区分：后端系统、前端原型、成品设计

Minihelp 当前采用 Python + FastAPI 的单体后端，通过 LangGraph 管理多轮对话与工具调用。现有功能分布在 API、图编排、模型与检索、工具、数据库以及静态管理页面中。它已经超出“聊天框调用一次模型”的范围，但完整的商业客服接待与交付体系仍在建设中。

05 / ORCHESTRATION

Agent 是受控流程，不是无限自由调用

图的主干是 resolve_reference → classify_intent → 条件路由。系统先补齐问题上下文，再判断应走哪条业务路径。在关键位置使用确定性节点，只有需要语言生成和灵活工具选择的环节交给主 Agent。

用户输入 → 指代消解 → 意图识别
↓ route_by_intent
商品咨询检索 → 证据门控
强：主 Agent；弱：兜底
退款退货 / 售后取订单 → 检索政策
→ 主 Agent
订单 / 物流 / 人工主 Agent
↔ 工具节点
投诉 / 闲聊 / 其他投诉应答或固定话术
→ 日志
↓
log_node → 保存 assistant 消息 → END

State 是一轮执行共享的上下文

messages 保存对话及工具消息；user_id / conversation_id 标识归属；resolved_query / intent / route 记录理解与分流；evidence / citations / evidence_strong 保存检索证据；order_data / suggested_actions 记录业务材料和页面动作；steps / tokens_used / trace 记录执行与观测信息。

消息通道通过 reducer 累积历史。运行入口会清空本轮专属字段，防止上一轮的退款卡片、引用和兜底回答残留到下一轮。conversation_id 同时被转成 checkpoint 的 thread_id，使同一会话可以多轮继续。

主 Agent 和工具之间如何循环？
  1. main_agent() 组装系统提示、摘要、近期历史与本轮证据，绑定可用工具后请求模型。
  2. 模型没有返回 tool_calls，就进入日志节点结束；有工具调用且未达到步数上限，则进入 agent_tools()。
  3. 工具结果变成 ToolMessage 回到消息列表，主 Agent 据此继续回答或调用下一工具。
  4. should_continue() 当前以有无工具调用和 max_agent_steps 决定是否继续。token 用量会记录，但这条条件边不以 token 阈值作为停止条件。
一个需要注意的实际实现细节

指代消解写入 resolved_query，意图识别使用它；但当前 retrieve_knowledge() 取的是 _user_text(state) 的原始问题，再交给 query_understanding 标准化。因此不能把现状描述为“所有检索都已经统一使用消解后的 query”。这也是后续应收敛的输入契约之一。

06 / REQUEST FLOWS

用四条链路理解一次请求

示例：“这款饮水机怎么清洗？”

  1. 浏览器提交消息

    原聊天页请求 POST /api/chat，携带用户标识、消息和可选会话 ID。当前 V2 原型尚未走这一真实链路。

  2. 运行入口记录用户消息

    runtime 检查会话，向 MySQL 写 user 消息，为 HumanMessage 设置 db-{msg_id} 锚点，并传入摘要信息。

  3. 图执行理解与路由

    指代消解、意图识别后，商品咨询进入 retrieve_knowledge，检索与质量门控在回答生成前完成。

  4. 主 Agent 根据证据生成回答

    证据充分时生成带引用的答案；不足则走兜底，避免用没有依据的产品信息硬答。

  5. 回复事件流传回页面

    runtime 输出 delta、citations、tool、interrupt、actions、done 等事件，API 再转为 SSE。只有指定回答节点的模型文本进入回答流。

  6. 保存回复并检查摘要

    log_node 保存 assistant 消息；轮后检查是否需要后台摘要。浏览器收到文字、数据库保存成功、客户最终看到回复，是不同层面的事实。

示例：“帮我建一个售后工单。”

  1. 模型提出 create_ticket

    模型给出描述与类型。agent_tools 先用工具 schema 校验，参数不齐时返回错误供追问，不直接写库。

  2. interrupt 暂停

    参数齐全后产生 confirm_ticket 中断，把 preview 交给页面。checkpoint 保存可恢复的图状态。

  3. 用户查看并确认

    页面请求 POST /api/actions/resume，提交 conversation_id 与 confirmed。runtime 使用 Command(resume=...) 继续执行。

  4. 执行引擎决定是否放行

    只有确认通过才向 execute_tool_call 传 confirmed=True。用户取消时生成拒绝执行的 ToolMessage。

  5. 写工单、审计、组织回复

    内置工单工具落库，结果回到 Agent，生成工单说明。现有另一个 create-ticket API 直接写 repository，两个入口尚未统一为完整应用服务。

已有确认机制不等于完整业务授权。成品仍需把确认绑定到服务端 action_id、用户、参数快照、版本与有效期，并以业务幂等防止重复办理。

示例：“我要退刚刚那笔订单。”

  1. 定位订单

    退款或售后意图进入 fetch_order，结合订单号和订单选择中断取得订单信息。当前订单来自 business.py 的稳定模拟数据。

  2. 查询售后政策

    retrieve_policy 取得政策证据，把订单与政策交给主 Agent 判断并解释。

  3. 提出退款表单

    submit_refund 在 agent_tools 被截成前端 refund_form 建议动作；这里先检查订单归属，不立即办理资金退款。

  4. 用户提交申请

    POST /api/actions/create-refund 把订单号和原因整理为描述，调用 repository.create_ticket，类型为“退款”。

  5. 得到退款工单号

    当前结果是售后申请记录。没有证据表明已对接真实支付退款、退款到账回调和财务对账。

订单工具里的归属校验不能替代所有写 API 的授权校验。现有 create-refund API 直接收订单字段并建工单，成品应统一调用售后应用服务，在可信身份下再次校验。

目标：客户要求人工后，AI 与客服不抢答 尚待实施

  1. 登记转人工请求

    服务端记录会话进入待分配状态，写入原因、优先级、店铺与当前控制版本。

  2. 分配或领取

    客服在权限范围内领取会话；数据库原子更新负责人，避免两个客服同时成功领取。

  3. 切换会话控制权

    更新接待模式并增加 control_version。正在运行的 AI 即使生成了回复，发送前也必须检查旧版本是否已经失效。

  4. 人工发送并跟进

    客服消息同样经过统一发送服务，记录发送结果与渠道回执；客户与工作台通过事件刷新。

  5. 结束或交回 AI

    记录交接内容与状态变化，需要时显式开启新的图运行代次，避免旧确认流程被误续跑。

原项目的转人工展示与 V2 的接管交互，并不等于已经具备上述完整服务端状态机。

07 / KNOWLEDGE

RAG 有两条管线：先建库，再查询

写入链：文档 → 可恢复的索引

文档文本当前以 Markdown 处理为基础
build_chunks()章节路径、内容类型、问法、正文
write_pending()MySQL 分块及前后邻居指针
↓
Embedding分批生成向量并检查维度
Milvus upsert主键使用 MySQL chunk ID
标记 done回填向量标识和完成状态

vectorize_pending() 扫描待处理分块；向量写入成功后再修改数据库状态。如果向量写成功但状态更新前失败，下次可按相同主键 upsert 重跑。这是一个可补偿的双写流程，不能称为 MySQL 与 Milvus 的跨库原子事务。

读取链：问题 → 证据 → 答案

  1. 查询理解：生成标准问法和关键词扩展；向量侧使用标准问法，BM25 可附加扩展词，降低语义污染。
  2. 召回：search_knowledge() 支持 vector、bm25、hybrid、hybrid_rerank 四种策略。复杂多问句可拆为子查询，再轮转合并与去重。
  3. 精排：将候选文本交给 rerank 模块，按与当前问题的相关性重新排序。
  4. 证据门控：计算证据置信度，低于阈值走兜底；再用 selfcheck 判断资料是否足够回答。
  5. 上下文组装：使用首尾排列组织重要资料，生成编号引用与 evidence 文本，交给主 Agent。
当前代码里的 pending/done 表示索引处理进度；成品还需要文档草稿、审核、发布、归档与版本切换。两组状态解决的是不同问题。PDF、扫描件和 Office 文档也不能仅靠上传按钮就视为已完成解析。

08 / STATE & DATA

三个存储各自保存什么

存储实际内容不能替代什么
MySQLconversations、messages、tickets、knowledge_chunks、faq、qa_extraction_staging、tool_audit_logs、low_confidence_questions、review_queue、eval_runs、faith_cases、topic_classifications业务记录不自动包含 LangGraph 的中断执行点
SQLite checkpoint按 thread_id 保存图执行状态与中断恢复信息不是统一的客户业务历史库，也不是业务操作幂等账本
Milvus知识文本、向量及检索相关字段不能承担会话权限、工单事务或文档发布事实源
进程内存运行中的图对象、工具注册状态、摘要任务登记；V2 的交互演示状态重启后可恢复的任务系统与分布式锁
文件与日志log/app.log、评测报告、训练与导出产物等不能只因存在文件路径就断言对应产物已生成或通过验收

长对话：摘要 + 最近消息窗口

把全部历史一直塞给模型会增加成本，也会降低重要信息的可见性。当前 build_window() 根据 summary_upto_msg_id 选择摘要之后的消息，并用 token 预算裁剪；模型上下文由系统提示、历史摘要、近期窗口与本轮材料组成。

maybe_schedule_summary() 在轮后检查新增消息数，达到阈值则用 asyncio.create_task 调用 run_summary()。后者读取旧摘要和新增对话片段，压缩后更新摘要与边界。进程内 _running 防止同进程重复调度，但不能当作跨进程锁或持久任务队列。

为什么 MySQL 消息和 checkpoint 都要有？

MySQL 消息回答“用户与客服说过什么”，用于业务展示、检索、审计和统计。checkpoint 回答“图运行到哪一步、持有什么状态、等待哪个输入”。例如用户还没点工单确认：业务库里已有提问，但图需要记住暂停位置，才能在确认后恢复。两者用途不同，也需要后续设计一致性与恢复策略。

09 / QUALITY LOOP

运营后台把问题反馈回知识与模型

现有后台的意义不仅是查看表格。它把在线问题、低置信度结果和评测报告连接起来，形成一条可人工审核的改进流程。

线上信号低置信度问题 / 用户反馈
候选与复核知识挖掘 / 去重 / 审核队列
知识补充审核后写入与向量化
离线评测检索效果 / 质量 / 成本变化

工具审计和模型观测是两类记录

工具引擎记录工具名、来源、参数、结果摘要、状态、耗时和重试次数；审计写入失败会记录日志，而不会把已完成工具执行反转成失败。模型调用通过日志及可选 Langfuse 观测，按会话、意图与用量分析。生产若要求强制审计，需要重新定义“审计失败时允许什么动作”的策略。

后台作业：已有白名单执行器，尚非持久 Worker

core/jobs.py 把登记的任务名称映射到固定命令，页面可触发重跑、读取进度与日志。前端不直接提交任意 shell 命令。该能力适合管理评测与课程任务，但不能据此认为已经具备业务消息的持久消费、租约、重试与重启恢复。

Ch10：旁路主题分类，而非实时接待的必备依赖

scripts/ch10/ 包含语料构建、预标注、数据集构建、训练、评估、ONNX 导出、推理与问题池分类脚本；后台有主题与验收入口。在线图仍调用自身意图识别模块，不应把主题统计分类器与在线业务路由混成一个系统。代码入口存在不代表本地权重、训练数据质量、导出产物和验收指标已经就绪；本次未运行训练或检查实际模型效果。

四组关键数据，让系统能对故障作出解释

  • inbox_event + message：记住渠道送来的事件是否处理过，以及它对应哪条业务消息。
  • turn_run：记住哪轮处理哪些输入、执行状态、配置版本、graph_thread_id 与 control_version。
  • pending_action + business_operation：前者保存待确认动作的参数和版本；后者以唯一 action_id 记录真实办理结果，防止重复执行。
  • outbound_message + business_event：记住回复是否已生成、已发送、是否有回执，以及工作台可回放的状态变化。
为什么已有 checkpoint 还需要这些业务记录？

checkpoint 能恢复程序执行，但不能自动保证外部副作用只发生一次。比如工单创建成功、回复模型失败，重跑图时必须识别“工单已创建”，不能再次创建。又如人工已接管、旧 AI 刚好生成完回复，发送前必须核对 control_version。业务状态、幂等与控制权需要独立于模型和图执行保存。

第一版为什么保留单 Worker 与 SQLite？

既有规划选择先限定为一个图执行进程，保留 SQLite checkpoint，配套备份与恢复。同一会话串行运行，减少多进程竞争。MySQL 任务记录承担持久化，内存队列只用于唤醒优化；没有实测瓶颈前不新增消息中间件。横向扩容之前，再验证共享 checkpoint 后端、任务租约和并发控制。

建议按能形成业务闭环的顺序实施

  1. 身份与会话基础：登录、店铺权限、统一消息契约、会话查询与状态；先把 V2 客户和工作台列表接到真实接口。
  2. 可靠接待：持久接入、轮次串行、生成与发送分离、断线恢复；完成一条真实聊天链路。
  3. 人工协同：排队、分配、接管、客服回复、结束与交回 AI；验证接管期间 AI 不再发送旧回复。
  4. 业务办理：统一工单与售后应用服务，绑定确认、参数快照、幂等与审计；接真实订单查询。
  5. 知识运营：文档解析、审核发布、版本与失败重试；保留原 RAG 评测与审核能力。
  6. 交付运维：数据库迁移、部署引导、备份恢复、依赖就绪、权限审计和升级回滚。
第一版完成的标准应是：一个客户消息能可靠进入，AI 或人工有明确接待权，业务办理可追踪，结果可送达，失败能恢复。主题分类训练属于增强能力，不应阻塞这个闭环。
